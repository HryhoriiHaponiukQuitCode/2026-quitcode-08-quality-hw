# Якість тестів: покриття, мутації, тести з AC

**Робоча ситуація: «100 % покриття — і дефект проходить».** У демо `leave-portal` (тег `ws8-00-baseline`) модуль
`src/lib/leave/calendar.ts` (перетин заявок, AC-LEAVE-11) має 100 % рядків, гілок і функцій. Заміните в рядку 14
`b.startDate <= a.endDate` на `<` — і весь набір лишиться зеленим: 119 з 119, а покриття `calendar.ts` — ті самі
100 / 100 / 100 / 100. Покриття каже, що код **виконався** під тестами. Воно не каже, що тест **упаде**, коли код
зламано. Stryker на цьому файлі дає 93,33 % (28 з 30): вижили два мутанти на `calendar.ts:14` — `<=` → `<` і умова →
`true`. Два тести з тексту AC — «нова заявка 02.11–03.11 закінчується в день початку заявки 03.11–04.11 —
OVERLAPPING_REQUEST» і «заявка 01.11–02.11 цілком раніше — приймається» — їх убивають: на тегі `ws8-02-tests` той
самий дефект дає `1 failed | 126 passed`, а Stryker — 100 % (30 з 30).

## Три міри — три різні питання

| Міра | Що каже | Чого не каже | Демо: `ws8-00-baseline` → `ws8-02-tests` |
|---|---|---|---|
| `npm run ac:coverage` | на кожен `реалізовано` AC є тест з AC ID у назві | чи цей тест щось перевіряє | OK, 27 з 27 → 27 з 27 |
| покриття рядків (v8) | який код виконався під тестами | чи тест упаде, якщо код зламати | 32,01 % (146 з 456) → **32,01 %**: нові тести не додали жодного рядка. Доменні файли: 11 з 14 — 100 %, `next-path.ts` 90 %, `dates.ts` 81 %, `messages.ts` 0 %; сторінки й дії — 0 % |
| mutation score | чи падає тест, коли код навмисно зламано | — це найближче до «сили» тесту | TS (Stryker, 505 мутантів): 80,59 % → 81,98 %; SQL: 6 з 11 → 10 з 11 + 1 еквівалентний |

Жодна міра не замінює іншої. `ac:coverage` — наявність, покриття — що виконалось, мутації — чи тест кусає. У демо
вісім нових тестів (119 → 127) не змінили ні `ac:coverage`, ні покриття, а мутації показали, що тести стали сильнішими.

## Покриття

- Провайдер `v8`, `@vitest/coverage-v8` — **рівно та сама версія, що `vitest`**.
- Окремий конфіг `vitest.coverage.config.mts`, тож `npm test` не змінюється. Запуск — `npm run test:coverage`, звіт —
  `coverage/index.html`; таблиця по шарах (спершу домен, найнижчі зверху) — `npm run coverage:summary`, у CI — Summary
  job «Покриття: доменна підлога».
- `include: ["src/**/*.{ts,tsx}"]`: без нього у звіт не потрапляють файли, яких жоден тест не імпортує (сторінки,
  дії).
- **Пороги — на файл і лише для доменних модулів**, які їх уже тримають (список `FLOORED` у конфігу; у демо — 9
  файлів з 90/85/90/90). На загальний відсоток поріг не ставимо: сторінки й дії доводять тести бази й e2e, а не це
  число. Храповик: файл додаємо в список, коли тести його піднімуть, і підлогу не знижуємо.
- **У сесії агента** Vitest ховає з термінальної таблиці файли зі 100 %. Цифри беріть з HTML-звіту чи
  `coverage/coverage-summary.json`.

| Що | Чи бачить JS-покриття | Чим міряти якість тестів |
|---|---|---|
| чистий TS (`src/lib/**`) | так | покриття як нижня межа + Stryker |
| Server Action (`"use server"`) | лише якщо тест її викликає (зазвичай ні: потрібні `cookies()`) | ядро дії з залежностями на PGlite + e2e |
| асинхронна серверна сторінка | ні: Vitest їх не рендерить | e2e |
| plpgsql, функції SQL | ні: вони працюють у Postgres, а не у V8 | SQL-мутації |
| політики RLS, GRANT, обмеження | ні, і жоден інструмент не дає покриття політик | SQL-мутації |

## Мутації TS: Stryker

**Що таке мутація.** Інструмент по одному змінює код: `<=` → `<`, умова → `true`, прибирає виклик. Після кожної зміни
він запускає тести. Тест упав — мутант **убитий**. Усе зелене — мутант **вижив**: цю поведінку жоден тест не охороняє.

- Версія — **10.1.1** (`@stryker-mutator/core` і `@stryker-mutator/vitest-runner`). Підтримка Vitest 5 з'явилась у
  10.1.0, але на npm 10.1.0 немає. **10.0.0 з Vitest 5 показує 0 %**: жоден тест не запускається, і всі мутанти
  «вижили». Інструмент для перевірки тестів теж треба перевіряти.
- Запуск на модулі за вашими AC: `npm run mutation:ts -- --mutate src/lib/<модуль>.ts`. Звіт —
  `reports/mutation/mutation.html`. `--incremental` перевикористовує результати минулого прогону. У демо: один файл —
  ≈5,5 с, увесь домен (505 мутантів) — ≈14 с.
- Тести бази Stryker не запускає (окремий `vitest.stryker.config.mts`): SQL доводять SQL-мутації.
- `cleanTempDir: "always"` у конфігу прибирає `.stryker-tmp/` з копією репо навіть після невдалого прогону. Якщо тека
  лишилась — видаліть її.
- `--logLevel debug` не додавайте: з vitest-runner 10.1.1 і Vitest 5 Stryker з ним падає (stryker-js #6272).

**Розбір вижилих на рядках ваших AC:**

| Категорія | Що це | Що робити |
|---|---|---|
| прогалина AC | тест не перевіряє межу чи випадок, названий в AC | тест з тексту AC (межа, обидва краї) |
| нерозрізнений вхід | тестові дані такі, що мутант дає той самий результат | інші дані з AC (наприклад, не лише «порожній список підрозділів») |
| дослівний текст | мутант змінює рядок повідомлення | доводить e2e/UAT: дослівний «Тоді» на сторінці |
| еквівалентний | поведінка справді не змінилась | `// Stryker disable next-line <Mutator>: <причина>` — лише з причиною, яку можна перевірити |

**Відсоток — не мета.** 70 % з чесним розбором краще за 95 %, отримані видаленням мутантів зі списку чи масовим
`Stryker disable`.

## Мутації SQL

Для відмовних AC правило зазвичай живе в базі: політика, GRANT, функція. JS-покриття його не бачить. Статистика
Postgres (`pg_stat_user_functions`) не рахує виклики, що закінчились `raise exception`, тобто якраз відмови. А покриття
політик RLS не дає жоден інструмент. Лишається одне питання: **чи червоніє тест, коли правило прибрати?** На нього
відповідає `scripts/mutation-check.mjs`.

**Мутант** — запис у `scripts/mutants.mjs`. Точний формат — у файлі з [`materials/`](../materials/README.md#b-якість-тестів).
Ілюстрація:

```js
{
  id: "R1",
  kind: "sql",
  ac: "AC-ROOM-06",
  file: "supabase/migrations/20261021000000_bookings.sql",
  tests: ["tests/db/bookings.test.ts"],
  what: "скасування: політика без умови власника",
  find: "using ((select auth.uid()) = owner_id)", // має зустрічатися у файлі рівно раз
  replace: "using (true)",
}
```

Без `kind: "sql"` `npm run mutation:sql` мутант мовчки пропускає.

- `npm run mutation:sql` — спершу прогін без мутацій (тести мають бути зеленими на чистому коді). Скрипт
  відмовляється працювати з незакоміченими змінами у файлі мутанта. Він тимчасово змінює міграцію (одна буквальна
  заміна: `$$` у plpgsql лишається `$$`), запускає лише названі тести бази й **завжди** повертає файл.
- **KILLED** — тест упав (правило охороняється). **SURVIVED** — усе зелене: тест з цим AC ID правило не охороняє.
- **ERROR** — тест-файл не завантажився, впав хук `beforeAll` (мутант зламав саму міграцію) чи Vitest не дав звіту.
  Це не «убитий»: у бал не рахується, а прогін червоний. Виправте `find` чи `replace`. У демо мутант із
  навмисно зламаним SQL дав `ERROR unrecognized exception condition "exceptio"`.
- `npm run mutation:sql -- --only L2,L5` — вибрані; `--markdown` — таблиця «мутант | AC | що зламано | вердикт | який
  тест упав» для опису PR; `--json reports/sql-mutation.json` — у файл.
- **Демо:** 11 SQL-мутантів ≈21 с (≈1,7 с на мутант). На тестах `ws8-00-baseline` — 6 з 11 вбито: вижили L2, L4, L5,
  L7 (L6 — еквівалентний, прийнятий з причиною). П'ять нових тестів бази — і на `ws8-02-tests` 10 з 11 + L6.
- **Послаблюйте умову до `true`, а не видаляйте політику.** Без політики RLS забороняє все, і тест відмови лишиться
  зеленим з неправильної причини. UPDATE з WHERE застосовує ще й політику SELECT: якщо тест не червоніє, можливо,
  рядок ховає друга політика.
- **Еквівалентний мутант** — лише з причиною, що посилається на рядок міграції, який робить його зайвим.
- Мутовану міграцію не комітьте ніколи. Застосовану міграцію в CI не змінюйте навіть тимчасово: `db-check` впаде з
  `CHANGED`.
- PGlite — це PostgreSQL 18, а `db-check` і `supabase start` — PostgreSQL 17. SQL, який приймає лише 18, пройде тести на
  PGlite і впаде в `db-check`. Тому `db-check` лишається обов'язковим поруч з тестами бази.

**Без PGlite-гарнесу** SQL-мутацій немає. Гарнес можна додати з
[`materials/testing/`](../materials/README.md#b-якість-тестів): `tests/db/supabase-pglite.ts` (`createTestDb()` →
`asUser` / `asAnon` / `asService`) і тест-перевірку `tests/db/profiles-db.test.ts` з мутантами P1 і P2 на `profiles`
шаблону (на чистому шаблоні обидва `KILLED`). Або чесно запишіть у proof pack, що SQL-правило мутацією не доведено.

## Запахи тестів

| Запах | Хто ловить |
|---|---|
| AC ID не на початку назви — `ac:coverage` тест не рахує | лінтер (`vitest/valid-title` з матеріалів) |
| `it.skip` / `.only` | лінтер (`no-disabled-tests`, `no-focused-tests`) |
| `try { … } catch (e) { expect(e)… }` — зелений, якщо нічого не кинуто | лінтер (`no-conditional-expect`, `no-conditional-in-test`); `requireAssertions` у шаблоні |
| тест без `expect` | лінтер (`expect-expect`); `requireAssertions` |
| `rejects.toThrow()` без тексту — проходить і на помилці в SQL | лінтер (`vitest/require-to-throw-message`); SQL-мутація |
| мок `rpc` чи вигадана помилка Postgres під AC ID | лише SQL-мутація: мутант у правилі лишає замоканий тест зеленим |
| TS-копія SQL-правила під AC ID | лише SQL-мутація |
| тавтологія: очікуване обчислено тією самою функцією | Stryker побічно: такий тест не вбиває жодного мутанта |
| «зручні» тестові дані, на яких мутант дає той самий результат | Stryker |
| помічник, якого сторінка не викликає | e2e / UAT |

Лінтер і `requireAssertions` прибирають дешеві запахи безкоштовно. **Що тест з AC перевіряє саме правило, доводить
лише мутація. Для SQL — лише SQL-мутація.**

Залежність тестів бази від порядку перевіряє перемішування:
`npx vitest run tests/db --sequence.shuffle.tests --sequence.seed=3` (кілька різних `seed`).

## Тести з AC, а не з коду

Агент, що пише тест, дивлячись на код, закріплює **поточну** поведінку разом з її помилками. Дослідження LLM-оракулів
кажуть те саме: вони здебільшого кодують те, що код уже робить. Тож оракул має йти з тексту AC, а мутація показує, чи
він кусає.

Правила для промпту чи скіла `ac-test`:

1. **Спершу текст AC**, дослівно (`openspec/specs/**` чи `requirements/`). Назва тесту починається з AC ID.
   Очікування — значення з «Тоді», а не значення, яке рахує код під тестом.
2. **Рівень — за таблицею нижче.** Відмова, правило якої живе в SQL, — тест бази на PGlite як `asUser` / `asAnon`
   плюс `asService`-читання «нічого не змінилося». Не TS-копія і не мок `rpc`.
3. **Спершу червоний.** Тест запускають без реалізації чи з прибраним правилом. Тест, що ніколи не був червоним, —
   не доказ.
4. **Межі, названі в AC, — обов'язкові кейси.** «Щонайменше 8» — тести на 7 і на 8. «Перетин» — обидва краї плюс
   «повністю раніше» і «повністю пізніше».
5. **Доказ мутацією в PR:** Stryker для TS, `mutation:sql` для SQL. Кожен вижилий на рядку AC — убитий або пояснений.
6. **Заборонено:**
   - `vi.mock` власних модулів (`@/lib/…`, крім `@/lib/supabase/*`, чи `@/app`) — лінтер з матеріалів це й забороняє;
   - `.skip` / `.only`;
   - `toThrow()` без тексту;
   - `if` / `try` навколо `expect`;
   - змінювати чи видаляти наявні тести в PR реалізації без рядка «чому».
7. **Хто пише код — не пише на нього тест.** Окрема сесія агента пише тести з AC, інша — код, що їх проходить
   (maker ≠ checker). У WS9 це стане правилом конвеєра.

## Який рівень для якого AC

| Форма AC | Рівень | Чому | Приклад з демо |
|---|---|---|---|
| розрахунок чи перевірка з межею («щонайменше 8», «не довше 200», кількість днів) | **unit** (Vitest) + Stryker | мілісекунди; мутація знаходить пропущену межу | AC-LEAVE-04 (кількість днів), AC-USERS-02 (довжина пароля) |
| відмова «X не може Y», яку тримає RLS, GRANT, тригер чи функція SQL | **база на PGlite** як `asUser` / `asAnon` + `asService` «нічого не змінилось» + SQL-мутант | лише справжній SQL це доводить: TS-копія й мок лишаються зеленими без правила | AC-USERS-08/09, AC-LEAVE-09 |
| правило двічі: TS для повідомлення, SQL як остання межа | **обидва**, кожен зі своїми межами | кожен шар може втратити правило окремо | AC-LEAVE-10, AC-LEAVE-11 |
| порядок перевірок у Server Action («admin-клієнт лише після перевірки ролі») | **ядро дії із залежностями-параметрами**: справжня перевірка ролі; підробки (`vi.fn`) лише для цих залежностей на стику (адреса в базі, Auth admin, пошта) | перевірку ролі робить справжній код, до запису справа не доходить; «не викликано» — шпигуном | AC-USERS-14/15/17 |
| точний текст чи стан, який бачить людина («Тоді» з повідомленням, редирект) | **e2e / UAT** (Playwright) | сторінки у Vitest — 0 %, дії — майже 0 %; асинхронні серверні сторінки Vitest не рендерить | AC-USERS-11 |
| сценарій двох ролей (адміністратор блокує день → у працівника змінюється кількість) | **e2e** | дві сесії, обчислення під час рендеру | — |
| налаштування платформи (лист, посилання, Redirect URLs) | **вручну** (PM) / RUNBOOK | ніде не емулюється | — |

Інший вибір з аргументом теж годиться: оцінюємо аргумент, а не збіг з таблицею.
