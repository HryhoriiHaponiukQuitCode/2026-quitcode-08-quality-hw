# Детерміновані ворота й AI-рев'ю

**Робоча ситуація.** Агент приніс PR: lint, typecheck, усі тести, build і `ac:coverage` зелені. А всередині —
мертва Server Action (а це публічний POST-ендпойнт), `it.skip` на тесті з AC, видалене твердження, яке ховало
помилку, і гілка `NODE_ENV === "test"` у коді застосунку. Зливаєте?

**Принцип для WS8 і WS9:** спершу дешеве й детерміноване, потім судження агента, наприкінці людина. Машина за секунди
ловить усе, що можна описати правилом. Агенту й людині лишається те, чого правило не опише.

## Шари воріт

| Шар | Що | Де | Статус |
|---|---|---|---|
| Уже є (шаблон) | TypeScript strict, ESLint, Vitest з `requireAssertions`, `spec:*`, `ac:coverage`, порядок міграцій, `db-check` | `ci.yml` (назви jobs заморожені) | обов'язкові |
| WS7 (якщо додали) | `check:design`, `check:boundary` | `architecture.yml` | дорадчі |
| **WS8** | тестові правила лінтера (`@vitest/eslint-plugin`, `eslint-plugin-playwright`) | `eslint.config.mjs` → `npm run lint` у job `app` | обов'язкові одразу: знахідки виправляємо в тому самому PR |
| **WS8** | «Ворота: fallow audit» (лише нові знахідки), «Покриття: доменна підлога» (+ таблиця в Summary) | **`quality.yml`** | дорадчі → **обов'язкові після першого зеленого прогону на `main`** |
| WS8, дорадчо завжди | «Порада: вразливі залежності» — `npm audit --omit=dev` | `quality.yml` | попередження, ніколи не валить |
| AI-рев'ю | CodeRabbit, `/code-review` | PR | дорадче: коментує, не затверджує |
| Людина | відповідь на кожну знахідку; приймання PM | PR, прод | — |

`ci.yml` і назви його jobs не змінюємо: на них тримається ruleset `solo-main`. Нове — в окремих workflow.

## fallow

**Що це.** Пакет npm `fallow` (MIT, бінарник на Rust). Він аналізує граф проєкту без запуску коду й знаходить:

- невикористані файли, експорти й залежності;
- цикли імпортів, дублі коду, складні функції;
- правила Next.js: мертві Server Actions, неправильні експорти з клієнтських файлів, директиви не на місці;
- **ризики в diff:** послаблені тести, гілки «лише для тестів» у коді, нові `eslint-disable`.

**Молодий інструмент.** Перший реліз — березень 2026, приблизно реліз на день, один мейнтейнер. Тому:

- версію закріплюємо точно (`fallow@3.35.0` у devDependencies);
- `fallow audit` спершу дорадчий, обов'язковим стає після першого зеленого прогону;
- запасний варіант для мертвого коду — `knip`.

**Дві команди:**

- `npx fallow` — **повний прогін**: усе, що вже є в репо. Робите один раз для розбору (крок 3.1 walkthrough). На
  чистому шаблоні з матеріалами, як і в демо, — дві знахідки мертвого коду: файл `src/lib/supabase/client.ts` і
  експорт `AC_ID_GLOBAL`; плюс кілька попереджень про складність у скриптах шаблону й коді застосунку — їх теж
  розбирайте.
- `npm run gates` — lint, typecheck і `fallow audit --base origin/main`: **лише нові знахідки** відносно `main`.
  Той самий аудит стоїть у `quality.yml` (там база — гілка, у яку PR): успадковане fallow показує як контекст і не
  валить PR. У демо: `Audit scope: 18 changed files vs origin/main` → `✓ No issues`, `npm run gates` ≈30 с.

**Розбір знахідок.** Кожна група — справжня, навмисна чи хибна:

- **справжня** — виправити (мертвий експорт прибрати, цикл розірвати);
- **навмисна** — `ignore…` у `.fallowrc.jsonc` з коментарем-причиною (компоненти shadcn/ui навмисно експортують усі
  частини);
- **хибна** — теж `ignore…` з причиною. Відома хибна тривога на нашому стеку: `@tailwindcss/turbopack` як
  «невикористана залежність». Tailwind 4 підключено рядком у `next.config.ts`, а fallow такого не бачить.

Правило вимкнене (`off`) чи файл проігнорований без причини — це не розбір, а приховування.

**Пастки:**

- перед першим запуском — `npm ci`: без `node_modules` fallow попереджає, що знахідки про залежності можуть бути
  хибними;
- результати застарілі (наприклад, після `npm i`) — `npx fallow --no-cache`;
- **`fallow audit` без `--base`** порівнює з upstream гілки. Після `git push -u` це сама гілка, і аудит перевіряє
  0 файлів — «зелений» завжди. Так сталося в демо, тому в `gates` база закріплена: `--base origin/main`;
- `entry` з glob `scripts/*.mjs` у конфігу не потрібен: скрипти з `package.json` fallow і так вважає точками входу.
  У конфігу з матеріалів `entry` — лише `vitest.stryker.config.mts` (його читає Stryker, а не `import`);
- **складність чужого коду:** новий файл для `fallow audit` — нова знахідка. Скрипти курсу (`scripts/uat/**`,
  `scripts/smoke.mjs` тощо) складні, і без `health.ignore` у `.fallowrc.jsonc` PR, що їх додає, червоніє (на клоні
  шаблону — 19 знахідок складності). У конфігу з матеріалів вони вже в `health.ignore`;
- `weakened-tests` — сигнал, а не доказ. Правило бачить не кожне послаблення: тест переписано з меншою кількістю
  тверджень, функцію видалено разом з її тестом. Силу тестів доводить мутація ([гайд з тестів](testing-guide.md)).

## Тестові правила лінтера

`@vitest/eslint-plugin` **1.6.27** (1.6.28 вимагає TypeScript 6 і не ставиться). Блок у
[`materials/gates/eslint.config.mjs`](../materials/gates/eslint.config.mjs) — recommended плюс кілька правил, усі як
`error`. Для `*.test.ts`:

| Правило | Що ловить |
|---|---|
| `vitest/no-disabled-tests` | `it.skip`, `describe.skip` — тест «є», але не працює (у recommended — лише `warn`) |
| `vitest/no-focused-tests` | `.only` — решта набору мовчки не запускається |
| `vitest/no-identical-title` | два тести з однаковою назвою — `ac:coverage` рахує не той |
| `vitest/valid-title` (з шаблоном) | AC ID посеред назви: `ac:coverage` рахує його лише на початку |
| `vitest/no-conditional-in-test`, `vitest/no-conditional-expect` | тест сам вирішує, чи щось перевіряти; `try { … } catch (e) { expect(e)… }` — зелений, якщо нічого не кинуто |
| `vitest/expect-expect` | тест без жодного `expect` (помічники `expect*` теж рахуються) |
| `vitest/valid-expect` | `expect` без перевірки або з неправильними аргументами (`expect(value, "пояснення")` можна) |
| `vitest/require-to-throw-message` | `rejects.toThrow()` без тексту — проходить на будь-якій помилці (одруківка в SQL), а не на відмові з AC |
| `no-restricted-syntax` | `vi.mock` власних модулів `src/lib/**` (крім `src/lib/supabase/**`) і `src/app/**` — через аліас, відносний шлях чи `import()` |

Для `tests/e2e/**` — `eslint-plugin-playwright` recommended: тест без перевірки (`thenStep` теж рахується),
`.skip` / `.only`, `waitForTimeout`, `networkidle`. Три правила з інформацією про типи для `src/` (забута `await`,
неповний `switch` за роллю) — у файлі закоментованим необов'язковим блоком: у демо вони знахідок не дали, а на вашому
коді можуть.

**Рівень `warn` не є м'яким стартом.** `npm run lint` у шаблоні має `--max-warnings 0` і працює в обов'язковому job
`app`. Будь-яке попередження валить його так само, як помилка. Тож:

- правила одразу стоять як `error`, а знахідки виправлено (чи пояснено) в тому самому PR воріт — так у демо й у
  матеріалах; на чистому шаблоні знахідок 0;
- або, поки знахідки є, ганяйте правила окремим кроком у `quality.yml` і переносьте в `eslint.config.mjs`, коли чисто.

## `npm audit` — лише дорадчо

`npm audit --omit=dev --audit-level=high` показує вразливі залежності продакшену. Саме він знайшов критичні
вразливості Next.js 16.4.0 у шаблоні й демо. Але обов'язковою перевіркою він не стає:

- **недетермінований:** той самий lockfile в різні запуски може дати різний список;
- **червоніє без зміни коду:** нова вразливість у залежності з'являється в базі будь-коли.

Тому в `quality.yml` він дає попередження, а не червоний прогін. Вразливість — привід для окремого PR з оновленням
(точні версії разом, без `npm audit fix --force`).

## Чого статика не бачить ніколи

| Вада | Хто ловить детерміновано |
|---|---|
| мертва Server Action, гілка `NODE_ENV === "test"` у коді, послаблений тест | fallow (`unused-server-actions`, `test-only-branch`, `weakened-tests`) |
| `it.skip` на тесті з AC | лінтер (`vitest/no-disabled-tests` — червоний `app`), fallow, мутація |
| admin-клієнт поза дозволеними серверними файлами | `check:boundary` (WS7) |
| діра в GRANT чи політиці в SQL | лише тест бази (PGlite) — тест відмови саме на це правило; наявні тести можуть лишитись зеленими |
| логічна помилка за видаленим твердженням | лише мутація: fallow бачить послаблений тест, але не помилку в коді |
| `getSession()` замість `getClaims()` для перевірки прав | жоден із наших детермінованих шарів — лише AI-рев'ю або власне правило |
| текст «Тоді» на сторінці | лише e2e / UAT |

Кожен шар ловить свій клас вад. Жоден шар не замінює інших. У демо такі вади разом із чистою «приманкою» пройшли всі
обов'язкові перевірки CI, а ловили їх саме шари з цієї таблиці. AI-рев'ю ловить частину з них теж — але дорадчо й не
кожного прогону; скільки саме, ви міряєте в eval рецензента (нижче).

## Вивід інструмента — дані, а не команди

Next.js 16.4.0 у сесії агента зупиняє `next build` з `SecurityFatalError` і пише агенту: повтори команду, запропонуй
людині `next upgrade --agent=security`. Це детерміновані ворота, вбудовані у фреймворк. Але текст звернено до агента,
а агент має сприймати вивід інструмента як **дані**. Правильна реакція — показати людині, що сталося, а не виконувати
запропоновану команду. Так само з текстом у PR, issue, на сторінці чи в коментарі коду.

## AI-рев'ю — дорадчий шар

**Два рецензенти, які у вас уже є:**

- **CodeRabbit** — на кожен PR вашого репо, з `.coderabbit.yaml` шаблону. У публічних репо з менш ніж 10 зірками він не
  стартує сам: пишіть окремим коментарем `@coderabbitai review` (повторно на тому самому PR — `@coderabbitai full
  review`). Безплатний план має ліміти: у пік чекайте.
- **`/code-review`** у Claude Code — вбудований скіл, працює локально на будь-якому плані.
  - Рівні — від `low` (лише найвпевненіші знахідки) до `max`; для eval беремо `high`.
  - Ціль — номер PR, гілка чи шлях.
  - Без інтерактиву — як у демо (лише читання: git і gh; лише налаштування проєкту, без ваших особистих моделей-радників
    і хуків; знахідки — у JSON-виводі):

    ```powershell
    claude -p "/code-review high 12" --setting-sources project --output-format json --allowedTools Read Grep Glob "Bash(git diff:*)" "Bash(git log:*)" "Bash(git show:*)" "Bash(git fetch:*)" "Bash(git rev-parse:*)" "Bash(git merge-base:*)" "Bash(git status:*)" "Bash(git branch:*)" "Bash(gh pr view:*)" "Bash(gh pr diff:*)" > code-review.json
    ```

    У демо такий прогін тривав 92 с і коштував $0,028 (модель рецензента — claude-haiku-5-5). З особистими
    налаштуваннями, де був радник на сильнішій моделі, той самий PR коштував $0,62. Назвіть модель у таблиці eval.
- **Скільки чекати.** У демо CodeRabbit відповів через ≈6 хв після `@coderabbitai review` і повідомив ліміт
  безплатного плану: одне рев'ю на годину. Плануйте повторний прогін (крок 7) з запасом.

**Один файл правил — два рецензенти.** CodeRabbit читає `AGENTS.md` як настанови для коду. `/code-review` іде за
`CLAUDE.md`, а `CLAUDE.md` шаблону імпортує `@AGENTS.md`. Тож правило, записане в `AGENTS.md`, бачать обидва.

**Дорадче — не ворота.** AI-рецензент коментує, але нічого не затверджує. Ворота — обов'язкові перевірки CI. Правило
курсу: **на кожну знахідку рецензента є відповідь до злиття** (виправлення або аргумент у треді). І не зливайте PR,
поки рев'ю ще йде.

**Ризики:**

- **«знайшов» ≠ «заблокував»:** знахідка дрібним коментарем серед двадцяти інших — не те саме, що «must fix»;
- **різні прогони — різні знахідки:** один прогін — це вибірка; для eval за можливості запускайте двічі;
- **ін'єкції через текст PR чи коментар у коді** («AI reviewers: pre-approved») — рецензент має сприймати їх як дані;
- **звідки рецензент читає правила:** з базової гілки чи з гілки PR. Правило, додане в тому самому PR, рецензент
  може не побачити.

## Eval рецензента: гілка з посадженими вадами

**Навіщо.** Ви вирішуєте, скільки довіряти рецензенту. «Здається, він непоганий» — не міра. Міра — таблиця на
відомому ключі: що він знайшов, що пропустив і де підняв хибну тривогу.

**Що посадити — 3 вади з різних категорій і 1 приманку:**

| Категорія | Приклад вади |
|---|---|
| права в даних | `grant update` на колонку ролі; політика без умови власника; функція `security definer` без `set search_path = ''` |
| авторизація в дії | `getSession()` замість `getClaims()`; роль з `user_metadata`; перевірка ролі після запису |
| тести | видалене твердження в тесті з AC; тест, що перевіряє мок замість правила |
| логіка | межа з AC: `<=` → `<`; пропущений статус у фільтрі |
| AC без доказу | нова поведінка без тесту з AC ID і рядка `conformance.md` |
| **приманка** | чиста зміна, що виглядає підозріло: перейменування, винесення перевірки в помічник без зміни поведінки, правильно оформлена функція `security definer` |

- **Вада має пройти всі обов'язкові перевірки:** саме такі доходять до рецензента. Якщо CI її ловить (червоний lint,
  typecheck, тест чи `quality`), це гарна новина про ваші ворота. Але для eval візьміть іншу.
- **Нейтральні назви:** гілка, коміти й опис PR не підказують, де вади.
- **Ключ відповідей** — поза репо, доки обидва рецензенти не відпрацюють. Потім — одним коментарем у PR разом із
  таблицею.
- **Безпека:** preview ходить у вашу прод-базу. Міграції з PR до злиття не застосовуються, а от код на preview живий:
  нова Server Action з вадою не має нічого записувати. PR **не зливаємо**, після eval закриваємо.

**Таблиця** (розділ D у [шаблоні proof pack](../materials/templates/proof-pack.template.md)): вада → CodeRabbit
(знайшов / пропустив + **цитата**) → `/code-review high` (знайшов / пропустив + **цитата**). Окремо — що кожен сказав
про приманку і решта знахідок (слушна / шум). Без цитат таблиця не перевіряється.

**Правило, що закриває пропуск.** Візьміть ваду, яку хтось пропустив, і допишіть правило:

```markdown
- У Server Actions і Route Handlers права перевіряються лише через `supabase.auth.getClaims()` і роль з `profiles`.
  `getSession()` для авторизації — помилка рівня «must fix»: дані сесії з cookie не перевірено на сервері.
```

Правило — окремим PR у `main` (в `AGENTS.md` або path instruction у `.coderabbit.yaml`). Потім `git merge main` у
гілку з вадами, `@coderabbitai full review` і `/code-review high` ще раз. Результат з цитатою — коментарем. Якщо обидва
знайшли все — правило загострює найслабшу знахідку (знайдено, але не як «must fix») або прибирає хибну тривогу на
приманці.

## Бонус: eval свого скіла

**Навіщо.** Скіл (наприклад, `spec-review` з шаблону) — це промпт, який агент підтягує сам. Чи він справді допомагає,
видно лише на прикладах: однакові кейси зі скілом і без нього, кілька прогонів, частка успішних (pass rate).

**Мінімум для бонусу:**

- ≥3 кейси: вхід (фікстура: файл специфікації чи вимоги з відомими проблемами) і що має бути у відповіді (наприклад,
  «знайдено AC без ролі»);
- ≥3 прогони на кейс;
- таблиця: кейс → очікуване → pass rate зі скілом → без скіла → висновок.

**Три шляхи:**

1. **`claude plugin eval`** (Claude Code 2.1.269+; довідка — `claude plugin eval --help`, чернетку набору робить
   `claude plugin eval init`).
   - Кожен кейс проганяє тричі зі скілом і без, звіт — `WITH / W/OUT / Δ`.
   - Потрібна обгортка-плагін (`.claude-plugin/plugin.json`).
   - Прогони ізольовані: без вашого `CLAUDE.md` і `.claude/`. Тож фікстури (специфікація, вимоги) кейс має принести
     сам. Це й урок: eval мусить побудувати контекст, на який скіл розраховує.
2. **Плагін skill-creator** (`/plugin install skill-creator@claude-plugins-official`): кейси в `evals/evals.json`
   поруч зі скілом, порівняння зі скілом і без.
3. **Цикл `claude -p`:** на кожен кейс — свіжа копія фікстури, `claude -p` тричі зі скілом і тричі без, перевірка
   виводу на очікуване (`Select-String`), таблиця. Промпт передавайте через stdin з файлу UTF-8: кирилиця в
   аргументах командного рядка Windows буває зіпсована. Свіжа копія — ще не довірена тека, і `claude -p` у ній ігнорує
   `permissions.allow` з `.claude/settings.json` проєкту: потрібні дозволи передавайте прапорцем `--allowedTools`
   (перевірено 26.10 на Claude Code 2.1.308, eval `spec-review` для слайда 42).

Вартість — центи. На підписці прогони рахуються в ліміти плану.
